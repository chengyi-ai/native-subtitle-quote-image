# 小红书个人品牌发布包

## 1. 定位与素材

读取用户指定的账号配置；未提供时复制 `assets/xiaohongshu-profile.example.json` 到任务目录，按已知目标填写并列出假设。默认面向 AI 时代的工程师、技术 Leader、产品经理，关注 AI 实践和技术转管理。不要声称用户属于某公司、有某项成果或已开售某产品。

素材发现优先查发布者官网、本人频道、官方访谈和有授权的用户自有视频。已有链接就先处理该链接；请求调研时用当前可用搜索工具找 3–5 个候选，记录标题、发布者、URL、发布日期、可用文字稿、候选时间段、使用权依据。不能访问时记为待核实，不虚构素材、热度或时间点。公开可看不等于有再发布授权。

读取用户明确提供的个人笔记或可公开案例，用“外部观点 + 我的实践 + 可执行建议”形成内容。没有个人实践时给出“可尝试的方法”，不要写“我带团队验证过”。未经用户指定，不读取或公开内部文档、客户数据、未公开专利方案。

## 2. 证据优先，再选题

给每个候选记录同一说话人的上下文与起止时间。证据未核实者只进入候选表，不能作为可发布引语。区分：

| 类型 | 写法 | 证据 |
| --- | --- | --- |
| 逐字引语 | 引号 + 人物 + 来源 | 已回看原文与时间段；正文逐字匹配 |
| 翻译 / 整理 | 明确标“译写 / 观点整理” | 原语言文本、译写文本、人工复核状态 |
| 个人解读 | “我的理解 / 实践建议” | 与引用分段；案例须来自可公开笔记 |

为证据已核实且允许复用的候选按 0–5 评分：受众匹配 30%、痛点具体 25%、行动价值 25%、商业关联 20%。总分 = 各项得分 × 权重 × 20。每项写一条理由。分数是编辑判断，不是爆款概率；名人影响力不能抵消证据缺失。只在同等素材中排序，选择 1 个主题推进。

从原稿核对否定词、条件、数字、说话人和上下句；不能把“可能”写成“必然”，不能为吸引点击编造“未来 3 年 50% 程序员……”等统计。封面改写归入个人解读，不能放进人物引号。标题、正文中每个引语用同一证据 ID 追踪。

## 3. 选择一个图文模板

以下是编辑预设，不是平台限制或流量保证。标题先生成 3 个候选，推荐 1 个；长度上限来自账号配置，不把未查证的平台限制写死。

| 模板 | 推荐标题结构 | 图序 | 正文结构 |
| --- | --- | --- | --- |
| 人物观点 | 听［人物］聊［问题］，我理解了［具体变化］ | 真实字幕图 → 来源和语境 → 独立解读 → 行动清单 | 原观点、适用条件、我的理解、一步行动 |
| 知识拆解 | ［具体难题］：用［方法］拆成［步骤数］步 | 问题 → 方法 → 可公开案例 → 清单 | 问题、方法、例子、边界、行动 |
| 成长实践 | 从［角色］到［角色］，先补［能力］ | 问题 → 亲历或假设场景 → 方法 → 练习 | 场景、判断、做法、可复用工具 |

人物图片调用原有渲染器，先完成模式确认和逐张 QA，默认请求小红书时用 1080×1440。知识/行动卡可先交付分镜文稿，使用可用排版工具单独绘制，不能宣称原渲染器已支持原创知识卡。个人解读不能混入人物字幕。每张图记录路径、角色、时间点和视觉检查状态。

正文建议 300–600 字，输出 3 个标题候选、封面编辑标题、正文、3–5 个相关话题、1 个低压力行动入口、来源和字幕模式说明。不要使用无根据的“震惊”“淘汰”“必看”等恐吓承诺。只有确实准备好的资料才写“领取资料”。

## 4. 商业设计

先选内容目的：discovery（吸引目标人群）、trust（建立专业信任）、conversion（验证需求）。每篇只选一个主要目的、一个主要 CTA。

- discovery：收藏 / 关注同主题后续；记录新增关注。
- trust：给出可执行工具或清单；邀请读者描述具体问题，记录有效需求反馈。
- conversion：只关联用户确认存在的服务或产品，说明适用人群、交付物和入口；不存在的产品留作验证假设，不写开售文案、价格或收入预期。

变现阶段从需求反馈 → 公开样例 → 小规模试交付 → 可重复产品递进；可以选择模板包、工作坊、课程或咨询，但不要预设用户具备企业咨询资质或交付资源。没有现成产品默认 trust + 收藏，不强插购买。价格、客单、收入、涨粉预测须由实际验证支持，不能沿用聊天里的示例数值当市场数据。

CTA 默认留在平台内。需要引流、商业合作标识或平台交易入口时，先用平台官方最新规则确认可用方式；不把“私信加群”当通用默认。Skill 只准备发布包；发布、主动私聊、加群和发送消息需用户明确指令。

## 5. 结构化输出与校验

复制 `assets/xiaohongshu-pack.example.json` 到任务目录。该文件是虚构演示，状态为 draft，不能当真实素材发布。将核对结果、标题、正文、独立解读、图片、商业设计填入，再运行：

```bash
python3 "<SKILL_DIR>/scripts/xiaohongshu_pack.py" pack.json --out-dir output-pack
```

输出 `post.md`（可复制图文）、`evidence.csv`（出处）、`strategy.md`（目的与商业假设）、`review.md`（草稿状态及待核对事项）、`metrics.csv`（待填实测数据）、`pack.json`（结构化原稿）。不覆盖已有输出目录。

草稿允许证据未核实或图片未交付，但必须列出缺口。仅在图文确已完成、引语和使用权均核实、每张图片打开检查后才设 `status: ready`。脚本会检查字段、时间序、逐字引语一致性、文件存在和显式核对状态；它不能核实实际视频、图片内容或平台规则。不得为了通过校验把未完成事项标 true。

脚本的长度检查以 Python 字符数计，配置只是编辑上限。检查当前平台规则和移动端预览后再确认最终发布格式。即使 ready 也不代表已经发布。

## 6. 手工反馈闭环

发布后由用户填写真实的 24h / 7d 曝光、阅读、收藏、关注、有效需求、订单、营收和生产分钟数；不同观察窗口分别记一行。拿不到的字段留空，不按零算。以收藏率=收藏/阅读、关注率=新增关注/阅读观察内容，以有效需求数和订单判断商业价值；没有平台归因时写“自报 / 人工归因”，不能把相关性说成因果。

同一主题、受众和观察窗口下比较标题或模板，每轮只改变一个因素。样本少时给“待验证假设”，不报告“某关键词提升 2 倍”的确定结论。用每篇实际生产时间判断是否值得继续自动化。定时采集和自动发布留作后续扩展，不假装当前已经接入平台 API。

## 7. 每轮保存完整推文与评分变化

每次迭代 Skill 的小红书能力，使用同一选题和受众产出一个完整版本。不要只留摘要或优化点。保存标题、封面、每页图文文字、完整正文、标签、CTA、Skill 版本、来源核验说明、优化点、六项得分及每项依据、未解决问题。已归档版本只能追加，不能重写；旧版存在事实问题时，在新版写更正并保留历史。

使用 `scripts/xiaohongshu_iterations.py`。以 [../assets/xiaohongshu-iterations.example.json](../assets/xiaohongshu-iterations.example.json) 为记录格式；它包含三版完整原创方法建议，均为未发布草稿，不冒充视频引语。创建新的真实主题时从 V1 开始，沿用相同受众、主题、固定评分口径。

```bash
python3 "<SKILL_DIR>/scripts/xiaohongshu_iterations.py" \
  --history history.json --revision revision-v1.json --report iterations.md
# 下一版只追加：revision-v2.json 中 version 为 2
python3 "<SKILL_DIR>/scripts/xiaohongshu_iterations.py" \
  --history history.json --revision revision-v2.json --report iterations.md
```

固定评分：受众匹配 20%、问题具体 20%、结构可读 15%、行动价值 20%、表达可信 15%、商业承接 10%。每项 0–5 分，总分由脚本计算。0=缺失，1=只有泛泛提及，2=部分明确，3=可用但有缺口，4=具体完整仍待验证，5=该维度已有可核对的完整依据；没有图片就不能据文字声称视觉满分，没有已验证产品就不能给商业承接满分。

这是推文文案的编辑自评，与前面的素材选题分数不同。草稿也可评价文案，但核验缺口必须同时展示，不能据此标为 ready。评审者优先保持一致，评分口径改变时另起系列。允许分数持平或下降；每个加减分说明具体文字变化。脚本使用快照哈希链检查历史一致性（非安全签名），导出总分及各分项的前后变化，不能代替独立评审或真实运营数据。

每轮至少解决一个明确缺口，跑校验与完整样例导出；连续两轮无实质改善时记录原因和下一项验证，不为涨分无限改写。发布后把同一版本 ID 与 metrics.csv 的实测窗口关联。
